# Comp HQ — Decisions log

Non-obvious choices made while building Comp HQ, in the format required by `PLAN.md` §2.4: one short paragraph each, headed `D-NN Title (task ID, date)`.

## D-77 The mark has one design file, and the servable SVG is generated from it (P5-05, 2026-09-21)

SPEC B11.2 asks for one source and no hand-exported sizes. The design lives in `tools/icons/comphq.design.svg`, which draws the sidebar's wordmark as live text in Big Shoulders Display. `npm run icons` (`tools/icons/render.mjs`) embeds the vendored font into it, writes `web/static/theme/icons/comphq.svg` (so the file draws identically on a computer without the font, which an SVG used as an image cannot fetch), and has the Playwright browser already used for the tests draw each PNG and the multi-size `.ico` from that. Drawing the letters as text rather than tracing outlines keeps them exactly the sidebar's, at the cost of the served SVG carrying the 35 KB font; a policy test proves the embedded bytes are the vendored font's. The regenerated files are committed and are not re-drawn in CI, because a browser's anti-aliasing differs between Windows and Linux and a byte comparison would fail for no real reason — instead tests check what matters: every size exists at its declared dimensions, the `.ico` entries are what they claim, the field is ink navy with an orange HQ, COMP is absent at 16 and 32, and the maskable icon's mark lies inside the safe circle. Gate 4.12's "the icon set is the fifteen line icons" test now skips `comphq.svg`, which is the app's own mark and not an interface icon (listed under "Tests corrected").

## D-76 The reading window may hold controls, in its Steps list only (P5-03, 2026-09-21)

Gate 4.23's test asserted that the task window's reading face contained no form control at all, as a way of proving the description is laid out as text and not sitting in a box. Phase 5 puts the Steps list in that same face (SPEC A11 gates 5.01–5.03: tick-boxes, an Add a step line), so the blanket assertion contradicted the spec. The test now excludes the `.task-steps` section from the count and keeps everything else it checked: the description still has no control, border or fill, and nothing else in the reading face may be a control. Listed under "Tests corrected" in the Phase 5 report.

## D-75 How the step store settles the edges SPEC leaves open (P5-01, 2026-09-21)

SPEC B4 fixes the limits and the two-people cases but not every edge, so the store settles them once, here, and every route inherits it. A tick or untick that changes nothing (ticking what is already ticked, unticking what isn't) and a move that leaves a step where it already is are quiet successes that write nothing and do not bump the change counter, so two people pressing the same box never make the other computer refresh for nothing. Undo into a full list of 50 is refused like any other add, otherwise remove-add-undo would get round the limit. "Removing a step somebody else already removed" is the only case that answers "Somebody else removed that step"; undoing a step that is already back is a quiet success, since the person's intent is already true. The removed row keeps its old `position` (the live steps are renumbered around it), which is how Undo knows where to go. Moving accepts both "up/down" and an absolute position, because the drag in P5-03 needs the latter and the store is the one place the ordering is maintained. Step words are one line: newlines and tabs become spaces, and the 200-character limit counts characters, not bytes.

## D-74 Removing a step offers Undo, not a "Removed steps" screen (P5-00, 2026-09-20)

Every other removable thing in Comp HQ has a screen that lists the removed ones and brings them back (Removed tasks, Removed events, article history), because losing a task or an event is expensive. A step is a line of text inside something that already has such a screen, and a whole list-and-restore screen for steps would be more machinery than three volunteers need. So A3 is honoured at the storage layer — `removed_at` is set, the row is never deleted, and it still appears in `steps.csv` — and at the interface an **Undo** appears beside the heading for about ten seconds or until the next action. If a step is lost after that, the job itself is in Removed tasks or in the nightly backup.

## D-73 Steps do not appear in the Saturday Briefing (P5-00, 2026-09-20)

The Briefing answers "what must be done by next Saturday and what's on" (A8). How far through its steps a job is doesn't change either answer, and a briefing that listed part-done steps would compete with its own three sections for the one screen that has to be readable at a glance on a Saturday morning. A job with unfinished steps briefs exactly as it did at v1.1.0, and a test asserts it, so this stays true by accident-proofing rather than by intention.

## D-72 No reusable step templates in v1.2 (P5-00, 2026-09-20)

The yearly jobs — the concert, the card campaign, exams — are exactly the case for a saved list of steps, and it was tempting. It needs a screen to make, name, edit and delete the templates, plus a picker on the job, which is roughly as much interface again as steps themselves. Copy last year's steps by hand this once (the old job is in Finished tasks, with its steps), and if that proves a nuisance in real use, templates become a small v1.3 with real evidence behind them rather than a guess.

## D-71 Ticking a step is not recorded in History (P5-00, 2026-09-20)

History on a job is there so somebody can see who changed what (gate 4.24). Ticks are the commonest action steps will produce — a twenty-step job could generate forty rows in an afternoon of ticking and unticking — and they would bury the changes History exists for. Adding, renaming, removing and restoring a step *are* recorded, because those alter what the job says. Who ticked a step and when is carried on the step itself ("Jane, Sat 19 Sep"), which is where anyone would look for it anyway. A test ticks ten steps and asserts History is unchanged, so this can't quietly erode.

## D-70 One flat list of steps per job, not several named lists (P5-00, 2026-09-20)

Trello allows several named checklists on one card. One flat list is quicker to read, needs no naming step when you add the first one, and removes a whole layer of interface (create list, rename list, remove list, and what happens to its items) from a screen that is already a window inside a board. A job that genuinely needs two groups of steps is usually two jobs, which the app models properly, with their own people, sizes and due dates. If real use disagrees, named groups can be added inside the existing table with one nullable column; the storage of B3 does not foreclose it.

## D-62 The task window is a native `<dialog>`, and the links stay the truth (P4-08 and P4-09, 2026-09-19)

**One `<dialog id="task-window">`**, opened with `showModal()`, rather than a hand-built floating box: the platform supplies Escape, the backdrop, the rest of the page going inert (Tab cannot reach the board behind it) and the return of focus, which is the simpler and more stable choice (A2 priority 2). `window.js` adds only what the platform doesn't: the close icon, Cancel, a click on the backdrop (only when the press *started* on the backdrop, so selecting text and letting go outside doesn't close it), and the "Leave without saving?" question (the same words and the same native `confirm` the Knowledge Base editor uses) when something has been typed. On close the keyboard goes back to the link that opened it. **Tab and the browser's own bar:** a native dialog lets Tab wrap round through the browser's address bar rather than trapping it; the test therefore asserts the keyboard is never on anything of the board, sidebar or top bar, which is what gate 4.26 says, not that it never leaves the page. **One form, two ways in:** the new-task form is one template (`tasks-new-form`) used by the page `/tasks/new` and, with `?fragment=1`, drawn on its own for the window (`app.RenderPartial`, no frame). The window posts the same form with a hidden `fragment=1`: a saved task answers `204` (the window closes and the board is swapped in place from the current page, so a filter survives) and a refused one answers `422` with the form again, message and typed values included. **How the no-JavaScript path is kept honest:** `+ Add task` is an ordinary link to `/tasks/new`; the script only intercepts a plain click. Two tests hold it: one with JavaScript switched off entirely (the page adds a task with every field), and one that makes the fragment request fail, where the click must still land on the page. If the save request itself fails to send, the form is submitted as a plain form with the fragment marker removed; if the save succeeded but the board refresh fails, the page reloads instead of resubmitting, so a task can never be added twice. **A fifth icon-only button:** gate 4.25 explicitly asks for a close *icon*, so `app.NewIconButton` gained `IconClose` ("Close", type button, `data-hook="window-close"`); it is the only icon-only button that isn't a card action, the policy test still requires a matching title and aria-label, and it is still the only place one can be written. **Reading and editing (P4-09):** a card's title is still a link to `/tasks/{id}` (the task's own page, unchanged, gate 4.27); a plain click opens the same window to read, from `GET /tasks/{id}?fragment=1` (`tasks-window-read`: size, column, due date, people, the description laid out as text with its line breaks kept, History behind a closed `<details>`, a primary **Edit**), and Edit fetches `&mode=edit`, the same form the task page uses (`tasks-details-form`, one template for both, ids unchanged; its label now says Description like the new-task form). Saving posts `POST /tasks/{id}` with `fragment=1` to the existing update endpoint: `204` shows the task again, reading, with History refreshed and the board swapped in place; `422` returns the form with a message and what was typed (the page now keeps typed values on a refused save too). History rows are the ones `ListActivity` already writes, so the window and the page show identical rows (tested). **Tests corrected:** every test that clicked a card title to reach the task page now goes to it by the link's address (`openTaskPage`, e2e/helpers/tasks.ts), because that click now opens the window, which is what gate 4.23 requires; the keyboard-only test of the details page reaches the page the same way. The window looks as though it had always been there because it is built only from the shared parts (card surface, panel-head rule, `.field`, `.btn`, the icon button); it has no picture in the mockup, so owner check O4.3 covers it.

## D-61c Test people are handed back when a test ends; the Board's people menu loads on demand (P4-07, 2026-09-19)

Two linked findings from P4-07's first CI run, which failed on the Team page's accessibility test. **Cause:** CI has 2 CPUs and so one Playwright worker, which means one server for all ~260 e2e tests, and every test signs in as a *new* person who then stays on that server for good. The Team view draws one lane per person and a people list inside every job, so by the end of a run the page had hundreds of lanes and tens of thousands of options: 25 s locally at the end of a single-worker run, over the 30 s limit on CI's slower machine. (The test count had simply grown past the point where it showed.) **Fix at the cause, not the limit:** `signInAsNewPerson` remembers the person's id from the cookie, and an automatic fixture in `e2e/helpers/fixtures.ts` removes those people through the existing test-mode route when the test ends (best effort; a server without the route is not a failure). The suite then keeps only the handful of people running tests need, as a real office does; the same single-worker run went from 5.5 to 4.8 minutes and the Team check from 25 s to about 2 s. No time limit was raised and no retry added. **Not weakened:** tests still create their own uniquely named data and never assume an empty database. **The Board's people menu** (gate 4.20) had first listed every person inside every card, which does not scale for the same reason; the circles are now a link to `/tasks/{id}/people` (a small page listing everyone, one button each: the no-script path) and board.js fetches the same list as a fragment (`app.RenderPartial`) to show as a menu on the card. The Team view's own per-job "Assign to…" list is unchanged here and is looked at again in P4-10.

## D-61 The day-first date field, and the shared parts (P4-03, 2026-09-19)

**The date field is a text box, not `<input type="date">`.** A native date input follows the *browser's* language, not the page's, so on this office's computers it showed `mm/dd/yyyy` and no attribute can change that. Of the options (three drop-downs; a script-drawn calendar; a text box) the simplest and most stable is a plain text box with the placeholder `dd/mm/yyyy`, checked on the server, so it works with no JavaScript and can't drift with a browser update. `internal/app/format` gained `ParseDayFirst` (accepts `25/09/2026`, `5/9/2026`, `05-09-2026`, `05.09.2026`, and the old `2026-09-25`), `NormaliseDate` (used where a handler reads the field: it turns a readable date into the stored ISO form and leaves anything else untouched), `DayFirst` (used where a handler fills the field back in) and `ValidISODate`. Storage is unchanged: dates are still ISO everywhere in the database and the exports. Because the browser no longer polices the value, the stores now refuse a due date, event date or "just this one" date that isn't a real day (`ErrInvalidDate`), with a plain message: "Please type the due date as day/month/year, like 25/09/2026." An American-order date such as `09/25/2026` is refused rather than silently read the wrong way. Times stay native `type="time"` (only the date is in gate 4.05). **Tests corrected** (each was asserting the old ISO display, which gate 4.05 changes): `internal/calendar/handlers_integration_test.go` (two assertions now expect `12/12/2026` etc., plus a new day-first test), `e2e/calendar/calendar.spec.ts` and `e2e/tasks/details.spec.ts` (date values), and the calendar keyboard-only test, which typed `10012026` into a native control's month/day/year segments and now types `01/10/2026` into the text box. **Shared parts:** stamps, size chips, people circles, workload blocks, the segmented switch, cards and panel heads are defined once in `theme.css`; the size chip, people stack and workload blocks are also shared template partials (`web/templates/app/parts.html`). A stamp and the switch are shared by CSS class alone, since a wrapper template would add nothing. Buttons are exactly `.btn` (primary/secondary), `.mini` (small), plus `.tb` (editor toolbar) and `.link-button`; every other control is a `.field` or `.check`; a policy test walks every template and fails on any control without one. **Avatars:** the twelve-hue palette is replaced by the mockup's four circle colours plus the accent circle for the person using the app (`internal/tasks.AvatarClass(personID, meID)`); `avatar_test.go` now proves the shipped CSS meets 4.5:1 for all five. **Also corrected:** the board drag test now scrolls both cards into view before dragging, because the taller form controls push the second card below a 768px window (the assertion and its retries are unchanged).

## D-58 Two flaky Knowledge Base search tests fixed at the cause (P3-05, 2026-09-18, caught by the release run's CI)

The gate 1.29 failure that had already appeared once (P2-15, passed on re-run) came back on the release commit, so this time it was traced instead of re-run. The test builds its word from a random suffix, and when that suffix ended in "s" the Porter stemmer no longer reduced "word" and "words" to the same root, so the search legitimately found nothing: a test-data bug, not an app bug (about one run in thirty). The word now ends in a fixed ordinary ending, so the plural rule is the only thing under test. Repeating the whole search file 15 times then exposed a second, rarer race in gate 1.32: it typed into the search box straight after sign-in, but sign-in doesn't wait for its own redirect and the picker page already counts as "ready", so the text could go into the page about to be replaced. It now loads /kb first, as its neighbours do. Both changes keep every assertion; 15 full repeats of the file (120 runs) now pass.

## D-57 One combined counter for the Briefing, and every Calendar write is a transaction (P3-03, 2026-09-18)

The Briefing changes when a task or an event does, so `GET /briefing/version` answers with `tasks_version + calendar_version`. Both only ever go up, so their sum moves on any single change and refresh.js needs no new mechanism, just the same `data-refresh-*` markers Tasks uses. ## D-50 The 2,000-task test library is a historical total, not 1,850 live cards on one screen (P2-12, 2026-09-18, caught by the speed test itself)

## D-48 documentElement.scrollWidth can lie once a page has a legitimate overflow:auto region (P2-09, 2026-09-17, caught by CI)

## D-46 Refresh design: a version counter, opt-in data attributes, and a body-level busy flag (P2-07, 2026-09-17)

## D-44 A per-row secondary query while a query's rows are still open deadlocks (P2-04, 2026-09-17, caught by a hung test)

`Store.ListActivity` renders "assigned"/"unassigned" activity by looking up the target person's name with a second query against `s.DB`, called from inside the loop iterating the first query's `rows`. With the app's single SQLite connection (`SetMaxOpenConns(1)`), that second query can't get a connection until the first one's `rows` are closed — but they never close, because the code waiting on that second query is itself inside the loop still holding them. The result isn't a wrong answer or a flaky test; it's a silent, permanent hang (`go test` only surfaced it because the run eventually exceeded its timeout). Fixed by draining the first query into a plain slice and closing its `rows` before rendering any row that might issue a second query. The general rule this confirms: with one shared connection, never let code that might issue its own query run while another query's `rows` on the same `*sql.DB` are still open — read fully, close, then process.

## D-41 De-flaking a pointer-based drag library under synthetic mouse input, and the real cause behind the residual failures (P2-03, 2026-09-17, caught by CI)

SortableJS drives its own drag via mouse/pointer events rather than the HTML5 Drag and Drop API, so `page.mouse` steps (not `locator.dragTo`) simulate a drag in E2E tests. Getting this reliable took several rounds: (1) the move endpoint's success response is a 302 redirect, so a naive `response.ok()` check after the drop flagged every successful drag as a failure — fixed by checking the status code directly; (2) the drag's start point had to move from the card's overall bounding-box centre to its title text specifically, since a centre point can fall inside the actions row that `board.js` deliberately filters (`filter: 'button, select'`) from ever starting a drag; (3) instead of guessing a wall-clock pause between synthetic mouse-move steps for SortableJS's own rAF-driven drag-start detection to catch up, `dragOnce` now polls (`page.waitForFunction`) for the `sortable-chosen` class SortableJS itself applies once a drag actually starts, which is correct regardless of how fast or slow the machine is. Fixed by switching both drag tests to the existing `fixtures-today.ts` test-scoped `server` fixture (tagged `@fresh`, the same pattern gate 2.03's OVERDUE test already uses), which starts each of them against its own empty board. The lesson: a synthetic-input flake that reproduces differently under different worker counts is a strong signal to check test data isolation before tuning timing further.

## D-40 A test-scoped server fixture for COMPHQ_TEST_TODAY (P2-01, 2026-09-17)

SPEC B4's `COMPHQ_TEST_TODAY` override needs to be set as an environment variable when the app process starts, but `e2e/helpers/fixtures.ts`'s `server` fixture is worker-scoped — one process, spawned once, reused by every test that worker happens to run — so it has one fixed environment for its entire lifetime. ## D-39 Avatar colours are a fixed CSS class palette, not inline styles (P2-01, 2026-09-17)

A person's initials-circle colour (PLAN.md P2-01: "a colour derived from the person id") was first built as a server-rendered `style="background-color: hsl(...)"`, marked `template.CSS` to stop `html/template`'s CSS sanitiser replacing it with its `ZgotmplZ` safety placeholder. The lesson generalises: this codebase's strict CSP means *any* future per-item dynamic styling needs a class-based palette, never an inline style, and a real browser check (not just template output) is the only way this class of bug gets caught before an owner sees a missing colour with no error anywhere.

## D-35 Content check E2E scopes to its own article, not a sitewide count (P1-36, 2026-09-17)

PLAN.md's own test description for gate 1.36 says "a clean library shows 0," but every E2E spec file in a run shares one server per Playwright worker (`e2e/helpers/fixtures.ts`), and `ListContentCheck` scans every published/archived article in the whole database — so a test asserting a literal sitewide "0" would be one flagged article away from failing depending on what else that worker happened to run first, with no way to control that ordering. The exact count is instead a Go-level test (`internal/kb`'s `TestListContentCheck*`, run against an isolated in-memory database per test); the E2E layer only proves the real HTTP/UI wiring, scoped to each test's own uniquely named article — the same pattern `e2e/kb/categories.spec.ts`'s tile-count test already uses (asserting "1 article" on its own category's tile, never a sitewide total).

## D-34 A Go helper to unzip the export in E2E, not an npm dependency (P1-35, 2026-09-17)

Gate 1.34's E2E check needs the downloaded export's contents as real files under a `file://` URL (an offline browser context, following links between actual pages) — Node has no built-in ZIP-format reader (only gzip/deflate streams), and adding a package like `adm-zip` just for one test would be the project's first npm devDependency added purely for test plumbing. `e2e/unzip` is a ~15-line Go program using the standard library's `archive/zip`, built once in `global-setup.ts` next to the existing `e2e/seed` binary and invoked the same way. Keeps the "at most five direct requirements" discipline (`tools/policy`'s `TestGoModAtMostFiveDirectRequirements`) working in spirit for the JS side too, and matches the project's existing preference for a small Go helper over a new dependency wherever the standard library already does the job.

## D-33 Backup status/banner design: success-only timestamp, test-mode seeding, fresh-install skip (P1-34, 2026-09-17)

Three separate decisions bundled into one task. First, `app_meta.last_backup_at` only ever advances on a *successful* `VACUUM INTO`; `last_backup_ok`/`last_backup_error` instead describe the outcome of the *most recent attempt*, which may be a later failure — this way `last_backup_at` always answers gate 1.35's literal question ("when did a backup last succeed") even after a subsequent failed night, while Settings can still separately show that the latest attempt failed and why. Second, an unconditional per-request banner check (`internal/app/frame.go`'s `RenderFrame`) would make every one of the hundreds of existing tests see a stale-backup banner, since a freshly started test server's `app_meta` has no `last_backup_at` row at all — fixed by having `cmd/comphq/main.go` seed a fresh timestamp via `db.SetLastBackupAtForTest` at startup when `COMPHQ_TEST_MODE=1` (used by every Playwright-spawned server), instead of running the real scheduler; a new test-mode-only route (`POST /__test/backups/set-last-backup-at`) lets a test move it to a stale value on demand for the one test that needs to see the banner. Third, the pre-update backup (`db.PreUpdateBackup`, called from `main.go` before running migrations, only when `db.HasPendingMigrations` is true for some section) also skips entirely on a truly fresh install — detected via `db.HasExistingData` checking for `app_meta`'s existence — because recording *any* backup result needs `app_meta` to already exist, and that table is itself created by the very first migration a fresh install hasn't run yet; there's also nothing meaningful in a brand-new database worth protecting with a backup anyway.

## D-32 One data-missing-kind CSS rule per value, not one shared message for all of them (P1-33, 2026-09-17)

`data-missing-kind` already existed before this task ("external", from a publish-time image-fetch failure, and "picture", from a Word-paste's unreachable clipboard image), both sharing one CSS `::after` message: "Picture not shown — use Import from Word to bring it in." ## D-31 Image bytes resolved up front into a plain lookup table; a picture-only paragraph isn't empty (P1-32, 2026-09-17)

Extracting a picture needs the zip package (to read and sniff the relationship's target bytes), but `document.go`'s token walker is deliberately pure — no I/O — so `docx.go`'s `Convert` now resolves every image-type relationship into a `resolvedImage` (`images.go`) *before* parsing starts: read via a new `readImagePart` (the existing `readPart`, generalised to take a caller-supplied limit so the per-image 20 MB cap and the whole-document 300 MB one compose correctly), sniffed with the same JPEG/PNG/GIF/WebP check `internal/kb/images.Store` uses for a real upload (re-implemented rather than imported, so this package stays free of any dependency beyond the standard library on this path), and never even attempted for a `TargetMode="External"` relationship. `parseBlocks` and its recursive re-parses (table cells, text boxes) now take a `*docCtx` bundling this lookup table alongside styles/hyperlink-rels and the running `[]Image`/token-counter state a whole `Convert()` call accumulates — a `<w:drawing>` or `<w:pict>`/`<w:object>`'s `v:imagedata` just looks its relationship id up in the map, either emitting a real `<img>` (with a `cid:` token the caller replaces once it stores the bytes — a scheme the sanitiser already rejects for anything else, so a token the caller somehow fails to replace is dropped, not left dangling) or a `data-missing-kind` placeholder. Wiring this up caught a real bug the same session it was written: `paragraph.hasContent()` had to become its own check, separate from `plainText()`, because a paragraph holding *only* a picture or placeholder has no text at all — the existing "drop empty paragraphs" rule was silently eating every picture-only paragraph, images included, until the fix.

## D-30 Tables via struct-decoding a captured subtree, re-parsed recursively (P1-31, 2026-09-17)

A table's row/cell nesting is naturally tree-shaped, unlike the free-form run content the flat token walk (D-28) suits well — so `document.go`'s `parseBlocks` special-cases `<w:tbl>`: on seeing its start token, `encoding/xml`'s `DecodeElement` consumes the whole element into a small struct (`tables.go`'s `tblXML`/`trXML`/`tcXML`), with each cell's own content captured as raw XML via the `xml:",innerxml"` tag rather than further unmarshalled. That raw XML is then fed straight back into `parseBlocks` itself (wrapped in a throwaway root re-declaring every namespace this converter reads, since a captured fragment carries none of its own) — so a cell gets exactly the same marks/links/list handling as a top-level paragraph, and a table nested inside a cell is "flattened into paragraphs" (SPEC B4) for free: it decodes into its own `tableBlock`, which `flattenBlocksToParagraphs` then splices into the outer cell's paragraph list by reading each of its cells' paragraphs in order, since nothing asked it to stay a nested `<table>`. The same DecodeElement-and-recurse pattern handles `w:txbxContent` (a text box's paragraphs, queued until the anchoring paragraph closes so they land right after it, per SPEC B4) and, together with a new `skipDepth`-gated check before either DecodeElement result is used, `mc:Choice` — this converter understands none of the extensions a Choice branch `Requires`, so it always prefers `mc:Fallback`, and gating on `skipDepth == 0` stops a text box or table present in *both* branches (a modern shape alongside its VML fallback, in particular) from being counted twice. The overall document's XML depth was already checked once, over the whole file, before any of this runs; a subtree can never be deeper than the whole it came from, so none of the recursive re-parses need a depth check of their own.

## D-29 Links as a segment attribute, merged the same way as marks (P1-30, 2026-09-17)

Hyperlinks (`w:hyperlink` with an external relationship, and legacy `HYPERLINK` simple/complex fields) needed to compose with bold/italic — a link can span a bold run and a plain run, and P1-29's segment model already merges adjacent same-formatting text into one span. Rather than a separate "link span" concept layered on top, `segment` gained an `href` field alongside `bold`/`italic`, resolved into a single `hrefStack` in `document.go`'s token walker (pushed by `w:hyperlink`, or by a `w:fldChar` "separate" once its instruction text parses as an external `HYPERLINK`, or by `w:fldSimple`'s own `w:instr` attribute; always popped at the matching end, even when nothing resolved, so an internal-anchor-only link or an unrecognised field still keeps its plain text with no href). Rendering became a two-level merge in `result.go`: group consecutive segments by `href` first (so a link spanning differently-formatted runs becomes one `<a>`, not several), then within each group, merge by bold/italic exactly as before. Lists are the one genuinely new structural piece: `paragraph` gained `directNumID`/`directIlvl`, resolved against either the paragraph's own `w:numPr` or (SPEC B4) its style's, via a new `styleSheet.numbering` basedOn-chain walk mirroring the existing outline-level one; `buildResult` groups consecutive same-numId paragraphs (after filtering empty ones, so a blank line doesn't split a list) and `renderList` builds the nested `ul`/`ol` structure with a small level stack, looking up each level's bullet-vs-other format in a new `numberingSheet` (`numbering.go`) parsed from `numbering.xml`.

## D-28 A per-run segment model for docx paragraphs, and a real fixture bug it caught (P1-29, 2026-09-17)

`internal/kb/docx`'s P1-11 spike reduced each `<w:p>` to one flat text string, enough for title/heading extraction but not for run-level formatting. P1-29 changes `paragraph` to hold `[]segment` (each a run of text with its own resolved bold/italic, or a line break), so a paragraph can mix "<strong>Sam</strong> before ordering more <em>toner</em>" in one line; `renderParagraphHTML` re-merges adjacent segments with identical formatting before emitting marks, so two runs split mid-word (a real Word artifact) still read as one word instead of two suspiciously-adjacent elements. Building this exposed a genuine bug in the P1-11 fixture generator: `image()`, `chartFrame()`, `smartArtWithFallback()` and `drawnShapeNoText()` all return a bare `<w:r>`, but several call sites in `sample.go`/`googledocs.go`/`big.go` spliced that bare run directly into the body as a sibling of `<w:p>` elements — not valid WordprocessingML (every `w:r` belongs to some `w:p`), and it silently discarded that content: the flat parser only ever appended a paragraph's `segments` to the result slice when its `<w:p>` closed, so text captured into a stray, paragraph-less run built up on a `paragraph` struct that had already been appended (or never would be) and was simply lost when the next real `<w:p>` overwrote it. Fixed by wrapping every such call in `p("", ...)` at its call site, and, defensively, by having the parser ignore a `<w:r>` encountered outside any `<w:p>` rather than silently losing whatever it captures.

## D-27 @verify-prev is skipped, not failed, when PREV never seeded anything (P1-28, 2026-09-17)

Implementing real `@seed`/`@verify-prev` content turned a CI-only bug from silent to loud: `run_upgrade_rollback_test`'s phase 2 always ran `@verify-prev` unconditionally, which is fine while it's a no-op placeholder but genuinely fails once it actually looks for seeded content — because PREV, right now, is always v0.0.1 (the highest existing tag until v0.0.2 is tagged), which predates the smoke-test harness and so never ran `@seed` in phase 1 to begin with. `run_prev_smoke` already had exactly the right check (does PREV's worktree even have smoke spec files?) for skipping phase 1 and phase 3's smoke assertions in this situation; phase 2's `@verify-prev` call now shares that same precomputed `prev_has_smoke_tests` flag instead of running unconditionally, so it's skipped for the same reason rather than failing against data that could never have existed. This is a bootstrap-only gap: once v0.0.2 is tagged and becomes PREV for some later `[container]` push, phase 1 seeds real content and `@verify-prev` runs and means something, same as gate 1.42 has always intended.

## D-26 container-test.sh reads its image tag from deploy/truenas.yaml instead of a hardcoded copy (P1-28, 2026-09-17)

Bumping `deploy/truenas.yaml`'s image tag to 0.0.2 broke the `container` CI job: `container-test.sh` had its own separate `IMAGE_REF="ghcr.io/stas-comp/comphq:0.0.1"` constant (from P1-06), so it built and locally tagged an `0.0.1` image while the Compose file it copied from `deploy/truenas.yaml` unmodified now asked for `0.0.2` — Compose tried to *pull* that (a real, unpublished tag) instead of using the image just built, and failed with "manifest unknown." Rather than also bumping that hardcoded copy at every future release (the same trap, waiting to be missed again), the script now derives `IMAGE_TAG` from `deploy/truenas.yaml` itself with `grep | sed -E` (not `grep -P`, which needs a PCRE build of grep and a UTF-8 locale neither of which this repo's Windows dev environment has, even though the Ubuntu CI runners do) — one version bump in one file is now enough.

## D-25 Fixed article identity, unique person, single-worker smoke project (P1-28, 2026-09-17)

`@seed`/`@verify`/`@verify-prev` (`e2e/smoke/basic.spec.ts`) prove gate 1.42 (an upgrade or rollback never loses Knowledge Base data) using content a later release's own `@verify-prev` has to recognise without having created it — so the article title and category name are fixed literals, not `uniqueName()`. The person who creates it, though, is a fresh one from `signInAsNewPerson`: `container-test.sh`'s upgrade/rollback harness runs `@seed` a second time against the *same* data folder once the build under test comes up (its phase 2, before the volume is ever wiped), and a fixed person name would collide with gate 1.06's duplicate-name refusal on that second run, where a category or article with a repeated name simply becomes a second row — harmless, and `@verify`/`@verify-prev` already select "the most recently updated" match rather than assuming there's only one. Locally, without `BASE_URL`, the `smoke` project also now runs with `workers: 1` (`playwright.config.ts`) for the same reason `speed` does (D-24): `@seed` and `@verify` only make sense run back-to-back against the one server that `@seed` just wrote to, and Playwright's worker-scoped `server` fixture gives every worker its own separate, empty database, so more than one worker silently breaks this suite's whole premise.

## D-24 Seeder design and timing method for speed tests (P1-27, 2026-09-17)

`e2e/seed` is a plain Go program, not a Playwright helper, so it can call `internal/kb`'s store types directly (`ArticleStore.Publish`, `CategoryStore.Create`, `images.Store.Save`) the same way the real app does, rather than re-implementing publish-and-sanitise logic over HTTP. It always runs to completion and exits *before* the real comphq binary opens the same `comphq.db` — the two never hold the file open at the same time — so there's no need to worry about SQLite's single-writer limit (D-02) between them. A single `math/rand` source seeded with a fixed constant drives every word, title and image chosen, so two runs with the same flags produce byte-identical content; that determinism is what makes a slow speed run reproducible rather than a one-off. The speed Playwright project (`e2e/speed/fixtures.ts`) seeds once by running with a single worker (`workers: 1` in `playwright.config.ts`) rather than by hand-rolling a global setup step, since a worker-scoped fixture already seeds exactly once per worker — one worker makes that a true "once" instead of once per parallel shard, and also keeps the timing measurements themselves free of CPU contention from other workers' tests. Timing itself uses plain `Date.now()` around `page.goto`+`data-ready`/`page.fill`+panel-visible/`page.request.get`, not Playwright's tracing API or `performance.now()` inside the page: SPEC B7's budgets are described in wall-clock terms a person would notice, and the median-of-5 (navigation, panel) or p95-of-50 (search endpoint) aggregation absorbs the noise a simple wall-clock timer carries.

## D-23 The server marks every matching block including the title; the client alone picks which to scroll to (P1-26, 2026-09-17)

A search result links to an article as `?q=<query>#b-<block>` (SPEC B4), but browsers never send the `#` fragment to the server, so the handler that renders the article page can't know which block the link meant to point at — only the query. The fix is to have the server compute every block the query matches (via `search.HighlightMatches`) and mark each one with a `data-hl` attribute holding its highlighted HTML, then let `highlight.js` — which alone can read `window.location.hash` — pick the one to scroll to and add the visible highlight class; every other matched block still gets highlighted in place, just without the scroll. This needed a block 0 for the title too: bm25 weights title matches 10x, so a query that matches an article's title often ranks the title as that article's single best-ranked block, meaning a real result can link to `#b-0`. The title lives outside `.kb-article-body` as its own `<h1>` rather than inside the sanitised `body_html`, so it needed its own `data-b="0"`/`data-hl` attributes threaded through a new `TitleHighlight` field, and `highlight.js`'s query scope had to widen from `.kb-article-body` to `document` to find it.

## D-22 Archive/unarchive share the article's current version_no (P1-24, 2026-09-16)

Every `kb_article_versions` row needs a `version_no` (SPEC B3), but archiving and unarchiving don't change an article's content — only its status — so they don't bump `kb_articles.version_no` the way a real edit does. Instead they insert a history row stamped with the version_no the article already has, holding a snapshot of the current title/category/body. That means two rows can share a version_no (e.g. an "edited" row and a later "archived" row both at version_no 3) — harmless, since `GET .../versions/{n}` just needs any row with that number, and they always agree on content. The alternative (bumping version_no on every status change too) would make "version 4" sometimes mean "different text" and sometimes "same text, different status," which is a worse distinction to explain than "some history rows share a number."

## D-21 A per-worker fixed loopback address for the SSRF test override (P1-23, 2026-09-16)

`COMPHQ_TEST_ALLOW_FETCH_HOST` (honoured only under `COMPHQ_TEST_MODE=1`) is read fresh from the environment on every fetch, which works for Go tests (`t.Setenv` mutates the same process) but not for E2E: the comphq binary is a separate OS process, spawned once per Playwright worker, and nothing can inject an env var into it after that. So `e2e/helpers/fixtures.ts` now reserves a *second* free port per worker at spawn time — alongside the comphq port it already allocated — fixes `COMPHQ_TEST_ALLOW_FETCH_HOST` to that `host:port` for the whole worker's lifetime, and exposes it as `server.stubImageHost`. A test that needs a reachable stub image server binds one to exactly that address (`e2e/helpers/stub-image-server.ts`); a test proving the failure path just points at that same address without starting anything, since a worker runs its own tests one at a time, so only one test ever holds the slot. `ArticleStore.Publish` also gained a transient `Article.ImageFailures` field (never written to the DB) rather than changing its return signature, since only two call sites care about it and every existing caller and test stays untouched.

## D-20 word.html scoped to SPEC B7's verification text, not the fuller gate prose (P1-22, 2026-09-16)

Gate 1.18's prose says pasting from Word keeps "headings, bold, lists, links and tables," but the existing `e2e/fixtures/paste/word.html` (from P1-10) has none of the last three — and Word's real clipboard HTML doesn't help: it fakes numbered lists with `mso-list` CSS on plain paragraphs plus a literal "1." text span marked `mso-list:Ignore`, not actual `<ol>/<li>` markup, so there's no simple universal HTML transform to reconstruct them. SPEC B7's own "how each gate is verified" table (the authoritative verification text, not the gate summary) only asks for: "the allowed elements are kept, style/font/class are stripped, and Word's file: pictures become placeholders with the Import from Word message" — all of which the existing fixture already exercises (headings, bold) plus the one thing that's specific to Word (the file: picture). Lists, links and tables from a paste are already proven by `web-page.html`, which uses ordinary HTML markup for all three. Reconstructing Word's fake lists is left out of scope here; it isn't asked for by B7 and would be a substantial feature of its own.

## D-19 Draining the request body before responding to an oversize upload (P1-21, 2026-09-16)

`internal/kb/images.Store.Save` reads only `MaxBytes+1` bytes via `io.LimitReader`, so an oversize upload leaves the rest of the body still arriving on the wire when `handleUploadImage` writes its 400 response. The E2E oversize test caught this directly: the browser's `fetch()` reported a generic network failure instead of delivering the 400, because the connection broke while the client was still sending. The fix is to `io.Copy(io.Discard, r.Body)` before writing the response in that one branch, so the client finishes uploading into the void and then cleanly receives the "larger than 20 MB" message. The other rejection (`ErrUnsupportedType`) doesn't need this — `Save` already read the whole body before sniffing it.

## D-18 Editor's initial content as JSON data, not an inline script; spike tests retired (P1-20, 2026-09-16)

The real editor page (`kb-editor.html`) needs to hand the article's existing `body_html` to `editor.js` before it creates the TipTap instance. An inline `<script>window.X = {{...}}</script>` is the obvious way, but the app's CSP (D-05's `default-src 'self'`, no `'unsafe-inline'`) blocks it outright — caught by the new editor E2E suite's CSP-violation test, not by inspection. Instead the value is written into a `<script type="application/json" id="article-initial-body-html">{{.BodyHTMLJS}}</script>` tag: browsers never execute non-JS-type script blocks, so CSP's script-src doesn't apply to it, and `editor.js` reads it with `JSON.parse(el.textContent)`. Separately, P1-09's `e2e/kb/editor-spike.spec.ts` (toolbar-command tests against the `/__test/editor` harness) is deleted now that the real editor has its own, more faithful E2E coverage (asserting the *published* article, not just the harness's live DOM); the harness itself (`/__test/editor`, `test-editor.html`, `test-editor.js`) stays, since `e2e/kb/paste-spike.spec.ts` (P1-10) still depends on it. Image upload is P1-21's job — P1-20's Image toolbar button inserts a `blob:` URL preview only, which `Sanitize` (SPEC B4) drops on publish since it isn't under `/images/`; expected until P1-21 wires up a real upload.

## D-16 Sanitiser link/image rules run as a custom pass after bluemonday (P1-18, 2026-09-16)

`internal/kb/html` uses `bluemonday` for the structural allowlist (tags and simple attributes like `colspan`/`rowspan`) but not for its own URL scheme/path checks. bluemonday's `RequireParseableURLs`/`AllowURLSchemes` validate `href` and `src` the same way across every element and reject relative URLs unless `AllowRelativeURLs(true)` is set globally — there's no way to say "keep the `<a>` tag but drop a `javascript:` href" (its default is to unwrap the whole element) while separately saying "drop the whole `<img>` unless `src` starts with `/images/`" (an attribute-value regex on `src` still leaves `alt` behind, so a bare `<img alt="...">` survives instead of disappearing). So `Sanitize` lets bluemonday allow `href`/`src`/`alt` unconditionally, then runs its own tree walk afterward: `fixLink` strips `href` unless its scheme is http/https/mailto and always adds `rel="noopener"`; `pruneInvalidImages` removes the `<img>` node outright unless `src` matches `^/images/`.

## D-17 Testing Publish's transaction rollback without a trigger on kb_search (P1-19, 2026-09-16)

PLAN.md's suggested test for `ArticleStore.Publish` injects a failure at the `kb_search` insert step to prove the whole save rolls back. SQLite refuses `CREATE TRIGGER` on a virtual table (`kb_search` is FTS5), so there's no way to force that exact statement to fail from a test without either restructuring the schema or bypassing the driver. Instead, `TestPublishRollsBackFullyOnError` edits an article with a `category_id` that doesn't exist: `kb_article_versions.category_id` (like `kb_articles.category_id`) has a real foreign key to `kb_categories(id)`, so this fails partway through the same transaction, after the `kb_articles` row has already been written but before the `kb_search` rewrite. Checking that the article, its version, and its search rows are all still exactly as they were before the edit proves the same all-or-nothing guarantee the plan was after.

## D-12 Paste/drop testing method (P1-10, 2026-09-16)

Chose a synthetic `ClipboardEvent`/`DragEvent` with a hand-built `DataTransfer` (approach (b) in the plan) over the real-clipboard approach (`context.grantPermissions(['clipboard-read','clipboard-write'])` + `navigator.clipboard.write`). It needs no OS clipboard or extra browser permissions, so it isn't sensitive to headless Chromium's clipboard support varying between Windows (dev) and Linux (CI). `e2e/helpers/paste.ts` exports `pasteFile`, `pasteHTML` and `dropFile`; all three ran green 40/40 (`--repeat-each=10` across the 4 paste/drop specs) locally before being committed at the normal `repeat-each=1`. The oversize-image fixture (`e2e/helpers/images.ts`) generates a real ~21–23MB greyscale PNG at test time with a small hand-rolled PNG writer (zlib deflate + CRC32) rather than committing one or depending on an image library.

## D-15 Section registry shape (P1-14, 2026-09-16)

`internal/app.Section` is a small struct (`MigrationName`, `Nav *NavItem`, `RegisterRoutes func(*http.ServeMux)`), not an interface — a section package exposes one `Section(srv *app.Server) app.Section` function, and `cmd/comphq/main.go` (which is the only place that may import every section, per SPEC B2 boundaries) adds one line per section: `srv.Registry().Add(briefing.Section(srv))`. `internal/app` itself only ever imports `internal/people` (an elevated, foundational dependency alongside `db` and `app` itself, per SPEC B2's boundary list), never a content section — the reverse dependency (section imports `app` to build handlers) would be a cycle otherwise. This supersedes D-14's "direct wiring" for every section except People and the app's own migration, which `NewServer` still registers itself since they're foundational rather than content sections.

## D-10 FTS5 query shape and markers (P1-08, 2026-09-16)

Confirmed `modernc.org/sqlite` v1.58.0 supports FTS5 `bm25()`, `snippet()` and `highlight()` identically to upstream SQLite, on Windows (dev) and Linux (CI) — no caveats found. Query building (`internal/kb/search.BuildQuery`): extract letter/digit runs only (`[\p{L}\p{N}]+`), discarding everything else, so raw user input can never inject FTS5 operator syntax; quote every run (`"word"`), which also defuses bareword operators like `AND`/`OR`/`NEAR`; suffix the last run with `*` for a prefix match — FTS5 allows `*` directly after a quoted string's closing quote for exactly this. Fewer than 2 significant characters yields no query at all (`ok = false`), rather than asking FTS5 to match everything or erroring. Snippet/highlight markers are the private-use characters U+E000/U+E001: they can't appear in real content and pass through `html.EscapeString` untouched, so the safe order is always escape-the-text-first, then replace markers with `<mark>`/`</mark>`. One gotcha: `snippet()` supports column index `-1` ("pick the column with the most matches"), but `highlight()` does not — `HighlightBlock` picks the column itself (0 for the title block, 1 for a body block) since SPEC B3 already tells us which one has content per row.
