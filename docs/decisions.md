# Comp HQ — Decisions log

Non-obvious choices made while building Comp HQ, in the format required by `PLAN.md` §2.4: one short paragraph each, headed `D-NN Title (task ID, date)`.

## D-45 A test-only route to backdate done_at, not a DB-seeding tool (P2-06, 2026-09-17)

SPEC gate 2.08's 14-day retention needs an E2E test that proves a task actually ages off the board into Finished tasks — but nothing in the app lets a real user (or a test acting as one) set `done_at` to the past; a task only gets a `done_at` the moment it enters Done, stamped with "now". Waiting 14 real days per test run isn't an option, and `e2e/seed` (the offline speed-test library generator) runs before the server starts and never touches a live database's rows, so it's the wrong tool for a single running test's fixture too. Fixed the same way `COMPHQ_TEST_TODAY` and the backups section's own `/__test/backups/set-last-backup-at` already solve this exact class of problem: a new test-mode-only route, `POST /__test/tasks/set-done-at` (task_id, days_ago), registered directly in `internal/app/server.go` against raw SQL on `tasks` rather than the `tasks` package's own `Store` — `internal/app` can't import a section, since every section already imports `internal/app` (D-14), the same reason `handleTestSeedKBArticle` above it talks to `kb_articles` directly instead of importing `internal/kb`.

## D-44 A per-row secondary query while a query's rows are still open deadlocks (P2-04, 2026-09-17, caught by a hung test)

`Store.ListActivity` renders "assigned"/"unassigned" activity by looking up the target person's name with a second query against `s.DB`, called from inside the loop iterating the first query's `rows`. With the app's single SQLite connection (`SetMaxOpenConns(1)`), that second query can't get a connection until the first one's `rows` are closed — but they never close, because the code waiting on that second query is itself inside the loop still holding them. The result isn't a wrong answer or a flaky test; it's a silent, permanent hang (`go test` only surfaced it because the run eventually exceeded its timeout). Fixed by draining the first query into a plain slice and closing its `rows` before rendering any row that might issue a second query. The general rule this confirms: with one shared connection, never let code that might issue its own query run while another query's `rows` on the same `*sql.DB` are still open — read fully, close, then process.

## D-43 Move never set done_at entering Done — a gap since P2-02, found while building P2-04 (2026-09-17)

`Store.Create` has set `done_at` for a task created straight into Done since P2-01 (needed because `ListBoard`'s 14-day retention query, gate 2.08, treats a NULL `done_at` as "never confirmed old enough to exclude" rather than as unfinished). `Store.Move` — the button moves from P2-02 and the drag-and-drop this same phase added in P2-03 — never got the equivalent treatment: dragging or button-moving a card into Done left `done_at` NULL forever, so gate 2.08 could never actually retire it from the board. Nothing caught this until P2-04's own `Update` needed the identical logic for a stage change made from the details form, at which point the gap in the existing `Move` code became obvious by comparison. Fixed with one shared `updateDoneAtForStageChange` helper, called from both `Move` and `Update` right after each writes the new `stage`: it sets `done_at` on entering Done and clears it on leaving, so the two paths can't drift apart again. Lesson: a helper that's "obviously" needed in a new code path is worth checking against every existing path that shares its precondition, not just the one being written.

## D-42 Vendor scripts sharing VENDOR.md must write rows in a stable order (P2-03, 2026-09-17, caught by CI)

`scripts/vendor-editor/build.mjs`'s and the new `scripts/vendor-sortable.mjs`'s `writeVendorEntry` both rewrote the shared `web/static/vendor/VENDOR.md` the same way: drop the existing row for their own asset, then append the fresh one at the end. That's order-stable as long as only one script ever touches the file, which was true until this task added a second one — CI's "editor bundle is reproducible" step (P1-09) re-runs only `vendor:editor` and diffs, so it always moves the editor row back to the end regardless of where it sat in the committed file, breaking reproducibility the moment a different vendored asset's row came after it. Fixed by having both scripts sort all rows (by their full line, i.e. effectively by name) before writing, so the file's content — and thus any future reproducibility check re-running just one of these scripts — no longer depends on which script last touched it or what order they ran in.

## D-41 De-flaking a pointer-based drag library under synthetic mouse input, and the real cause behind the residual failures (P2-03, 2026-09-17, caught by CI)

SortableJS drives its own drag via mouse/pointer events rather than the HTML5 Drag and Drop API, so `page.mouse` steps (not `locator.dragTo`) simulate a drag in E2E tests. Getting this reliable took several rounds: (1) the move endpoint's success response is a 302 redirect, so a naive `response.ok()` check after the drop flagged every successful drag as a failure — fixed by checking the status code directly; (2) the drag's start point had to move from the card's overall bounding-box centre to its title text specifically, since a centre point can fall inside the actions row that `board.js` deliberately filters (`filter: 'button, select'`) from ever starting a drag; (3) instead of guessing a wall-clock pause between synthetic mouse-move steps for SortableJS's own rAF-driven drag-start detection to catch up, `dragOnce` now polls (`page.waitForFunction`) for the `sortable-chosen` class SortableJS itself applies once a drag actually starts, which is correct regardless of how fast or slow the machine is. Even after all of that, the real remaining cause of the "dragging a card to another column" test's failures (100% locally under `--workers=1`, and the same failure CI hit) was a plain test-isolation bug, not drag-simulation flakiness at all: this file's default `server` fixture is worker-scoped and long-lived, reused across every other board test with no way yet to delete a task (P2-06), so by the time these two drag tests ran, "doing"'s column already held enough accumulated cards from earlier tests to push the anchor card below the fold — `boundingBox()` doesn't scroll anything into view, so the "drag" was moving the mouse over blank page space the whole time. Fixed by switching both drag tests to the existing `fixtures-today.ts` test-scoped `server` fixture (tagged `@fresh`, the same pattern gate 2.03's OVERDUE test already uses), which starts each of them against its own empty board. The lesson: a synthetic-input flake that reproduces differently under different worker counts is a strong signal to check test data isolation before tuning timing further.

## D-40 A test-scoped server fixture for COMPHQ_TEST_TODAY (P2-01, 2026-09-17)

SPEC B4's `COMPHQ_TEST_TODAY` override needs to be set as an environment variable when the app process starts, but `e2e/helpers/fixtures.ts`'s `server` fixture is worker-scoped — one process, spawned once, reused by every test that worker happens to run — so it has one fixed environment for its entire lifetime. Gate 2.03's OVERDUE test needs a specific "today"; Phase 3's Briefing tests will need several different ones in the same run (PLAN.md: 2026-09-19, 2026-09-16, 2026-09-12), which a shared worker-wide server can't offer at all. `e2e/helpers/fixtures-today.ts` adds a second, deliberately separate `server` fixture, test-scoped (Playwright's default) rather than worker-scoped, parameterised via a `today` fixture option (`test.use({ today: '...' })`) — a new process per test that needs one, thrown away afterward. Every test using it is tagged `@fresh` in its title: like any test needing its own private server, there's no way to control a shared container's or shared worker's idea of "today" in `BASE_URL` mode.

## D-39 Avatar colours are a fixed CSS class palette, not inline styles (P2-01, 2026-09-17)

A person's initials-circle colour (PLAN.md P2-01: "a colour derived from the person id") was first built as a server-rendered `style="background-color: hsl(...)"`, marked `template.CSS` to stop `html/template`'s CSS sanitiser replacing it with its `ZgotmplZ` safety placeholder. That rendered fine as HTML, but manually exercising the feature in a real browser (not caught by any automated test, since none of them checked computed styles) showed the colour never actually appeared: the app's CSP is `default-src 'self'` with no `unsafe-inline` for `style-src` (which falls back to `default-src`), and Chromium silently drops an inline style attribute under that policy rather than applying it — the attribute stays in the DOM, unlike a script the browser would at least log loudly. Fixed by pre-defining 12 `.task-avatar-N` classes in `board.css` (evenly spaced hues, all `hsl(*, 50%, 25%)` — chosen because that saturation/lightness combination clears WCAG AA's 4.5:1 contrast for white text at *every* hue, verified by testing the actual worst case, yellow, not just the twelve in use) and having Go pick a class name instead of a colour value. A test (`TestAvatarColorClassCSSMatchesGoPalette`) parses the real CSS file to keep it from silently drifting out of sync with the Go side's `avatarColorCount`/`avatarHue`. The lesson generalises: this codebase's strict CSP means *any* future per-item dynamic styling needs a class-based palette, never an inline style, and a real browser check (not just template output) is the only way this class of bug gets caught before an owner sees a missing colour with no error anywhere.

## D-37 BASE_URL-mode E2E fixes for the offline full-suite run; separate tags for the restart sub-test's name check (P1-38, 2026-09-17)

Running the full `e2e` Playwright project against the offline container (gate 1.41) surfaced, by inspection, three existing tests that only worked because each Playwright worker normally spawns its own private server: `e2e/kb/external-images.spec.ts`'s "reachable" test needs a real local stub image server (impossible against a container with no internet by design, and `server.stubImageHost` is deliberately empty in `BASE_URL` mode anyway) — tagged `@fresh`, which `playwright.config.ts` already excludes whenever `BASE_URL` is set. Its "unreachable" test, and the P1-36 Content check test that copied its pattern, both built their target URL from that same empty `server.stubImageHost`, which would have produced a malformed URL — both now use a new shared constant, `UNREACHABLE_IMAGE_URL = 'http://127.0.0.1:1/gone.png'` (`e2e/helpers/stub-image-server.ts`): the app's own SSRF guard refuses any loopback address outright, so this fails fast and identically whether there's real internet, no internet, or a per-worker stub server, with no per-environment plumbing needed at all — arguably a better fixture than the original for a test that only needs *some* fetch failure. `e2e/kb/import-word.spec.ts`'s shared `expectSampleDocxImported` helper's on-disk file check is now skipped when `server.dataDir` is empty, rather than tagging its two calling tests `@fresh` — losing them from the offline run would mean gates 1.45–1.49 (all of Word import) never get proven with no internet access at all, and every *other* part of that helper's assertions works fine against a shared container.

Separately, the restart sub-test's new "names intact" check (gate 1.39) needed a fixed person name, unlike `e2e/smoke/basic.spec.ts`'s deliberately-random one (that file's own comment explains why: its `@seed` test runs twice against the same data folder during the upgrade/rollback sub-test, and a fixed name would trip gate 1.06's duplicate-name refusal on the second run). Rather than risk that file's delicate design, the name check lives in a new `e2e/smoke/names.spec.ts` with its own `@names-seed`/`@names-verify` tags — picked specifically so neither literal substring "@seed" nor "@verify" appears in them, since `container-test.sh`'s existing upgrade-rollback grep patterns (`@seed|@verify(?!-prev)`) match anywhere in a test's title, scoped to the whole `smoke` project, not to one file.

The first two real `gh workflow run ci.yml -f full=true` dispatches (static review alone couldn't have caught these) failed and were fixed in follow-up commits: (1) `checksum_data_dir` failed with "Permission denied" the first time step 2b actually made the app write a real uploaded image — `images.Store` writes files uid 568 mode 0600 (`os.CreateTemp`'s default, entirely correct for the container, which only ever reads its own files), unreadable by the different host user running the checksum; fixed by running that one `sha256sum` step under `sudo`, matching the existing `sudo tee` used for the marker file. (2) `e2e/settings/export.spec.ts` needs the `e2e/unzip` helper in `BASE_URL` mode too, but `global-setup.ts`'s early return for `BASE_URL` skipped building it entirely; fixed by hoisting that one build above the early return — but only running it when the binary doesn't already exist, since the offline sub-test's second "runner" invocation (`--project=e2e`) has no Go toolchain at all (`mcr.microsoft.com/playwright` is a Node image) and must instead reuse the copy an earlier host-side step (which does have Go) already built into the bind-mounted repo. (3) Two `e2e/settings/settings.spec.ts` tests baked in assumptions true only for a loopback-addressed server: "About shows the version" hardcoded the per-worker build's fixed `"0.0.0-test"` rather than accepting whatever real version the container under test actually carries; "Copy puts the exact command text on the clipboard" only asserted the Clipboard API's success path, never `copy.js`'s own documented select-text fallback — which fires here because Chromium treats only loopback addresses as a secure context regardless of scheme, and the container is reached over the Compose hostname `comphq`, not an IP. That fallback is exactly what a real owner already sees today, reaching Comp HQ over plain HTTP at a NAS IP address (also not loopback) — a preexisting, correct product behavior this task's hardening simply exercised for the first time, not a bug to fix in the app.

## D-36 GitHub's two one-time steps get no README walkthrough of their own (P1-37, 2026-09-17)

SPEC A13's hands-on-moments table includes two GitHub actions (signing in once before building starts, and switching the package to public after the first release), and B8 rule 7 says "click-by-click instructions for every owner hands-on moment in A13." Both of those two are things the *build agent* prompts the owner to do at the exact moment they're needed — not something the owner would ever look up in the README on their own initiative, since there's no everyday trigger for either (unlike, say, "the app won't open," which the owner discovers by themselves). ## D-35 Content check E2E scopes to its own article, not a sitewide count (P1-36, 2026-09-17)

PLAN.md's own test description for gate 1.36 says "a clean library shows 0," but every E2E spec file in a run shares one server per Playwright worker (`e2e/helpers/fixtures.ts`), and `ListContentCheck` scans every published/archived article in the whole database — so a test asserting a literal sitewide "0" would be one flagged article away from failing depending on what else that worker happened to run first, with no way to control that ordering. The exact count is instead a Go-level test (`internal/kb`'s `TestListContentCheck*`, run against an isolated in-memory database per test); the E2E layer only proves the real HTTP/UI wiring, scoped to each test's own uniquely named article — the same pattern `e2e/kb/categories.spec.ts`'s tile-count test already uses (asserting "1 article" on its own category's tile, never a sitewide total).

## D-34 A Go helper to unzip the export in E2E, not an npm dependency (P1-35, 2026-09-17)

Gate 1.34's E2E check needs the downloaded export's contents as real files under a `file://` URL (an offline browser context, following links between actual pages) — Node has no built-in ZIP-format reader (only gzip/deflate streams), and adding a package like `adm-zip` just for one test would be the project's first npm devDependency added purely for test plumbing. `e2e/unzip` is a ~15-line Go program using the standard library's `archive/zip`, built once in `global-setup.ts` next to the existing `e2e/seed` binary and invoked the same way. Keeps the "at most five direct requirements" discipline (`tools/policy`'s `TestGoModAtMostFiveDirectRequirements`) working in spirit for the JS side too, and matches the project's existing preference for a small Go helper over a new dependency wherever the standard library already does the job.

## D-33 Backup status/banner design: success-only timestamp, test-mode seeding, fresh-install skip (P1-34, 2026-09-17)

Three separate decisions bundled into one task. First, `app_meta.last_backup_at` only ever advances on a *successful* `VACUUM INTO`; `last_backup_ok`/`last_backup_error` instead describe the outcome of the *most recent attempt*, which may be a later failure — this way `last_backup_at` always answers gate 1.35's literal question ("when did a backup last succeed") even after a subsequent failed night, while Settings can still separately show that the latest attempt failed and why. Second, an unconditional per-request banner check (`internal/app/frame.go`'s `RenderFrame`) would make every one of the hundreds of existing tests see a stale-backup banner, since a freshly started test server's `app_meta` has no `last_backup_at` row at all — fixed by having `cmd/comphq/main.go` seed a fresh timestamp via `db.SetLastBackupAtForTest` at startup when `COMPHQ_TEST_MODE=1` (used by every Playwright-spawned server), instead of running the real scheduler; a new test-mode-only route (`POST /__test/backups/set-last-backup-at`) lets a test move it to a stale value on demand for the one test that needs to see the banner. Third, the pre-update backup (`db.PreUpdateBackup`, called from `main.go` before running migrations, only when `db.HasPendingMigrations` is true for some section) also skips entirely on a truly fresh install — detected via `db.HasExistingData` checking for `app_meta`'s existence — because recording *any* backup result needs `app_meta` to already exist, and that table is itself created by the very first migration a fresh install hasn't run yet; there's also nothing meaningful in a brand-new database worth protecting with a backup anyway.

## D-01 Name and identifiers (P1-02, 2026-09-16)

The app is named Comp HQ (owner, 14 Sep 2026). All identifiers use `comphq` / `COMPHQ_*` (repository `stas-comp/comphq`, binary `comphq`, container image `ghcr.io/stas-comp/comphq`, environment variables prefixed `COMPHQ_`). `SPEC.md` was updated accordingly.

## D-02 Single SQLite connection (P1-03, 2026-09-16)

`internal/db.Open` sets `sqlDB.SetMaxOpenConns(1)`. SQLite allows only one writer at a time; a single shared connection is the simplest way to avoid "database is locked" errors, at the cost of serialising reads too. Revisit if the layer 5 speed tests (P1-27) show read contention — a common fix is a second, read-only connection pool.

## D-03 Embedding at the repository root (P1-03, 2026-09-16)

`go:embed` patterns can't reach outside the directory of the file that declares them, but `web/` and `migrations/` are siblings of `internal/` and `cmd/` (SPEC B2's layout). So the embed directives live in a small package at the repository root (`assets.go`, `package comphq`), imported by `internal/app` and `cmd/comphq`. Every later section's templates and migrations are covered automatically since the patterns are `all:web/templates` and `all:migrations`.

## D-32 One data-missing-kind CSS rule per value, not one shared message for all of them (P1-33, 2026-09-17)

`data-missing-kind` already existed before this task ("external", from a publish-time image-fetch failure, and "picture", from a Word-paste's unreachable clipboard image), both sharing one CSS `::after` message: "Picture not shown — use Import from Word to bring it in." Wiring up the real converter's five *other* kinds (chart/diagram/shape/equation/object) to that same rule would have shown that exact sentence for a missing chart or equation too — wrong noun, and "use Import from Word" makes no sense when Import from Word is what produced the placeholder. `editor.css` now has one `[data-missing-kind="..."]::after` rule per value ("Picture not shown.", "Chart not shown.", ...), reserving what to actually *do* about it for the one-off status message shown alongside (`ComphqMessages`), not the permanent in-place label — a distinction that wasn't previously load-bearing when there was only one kind of picture failure to describe.

## D-31 Image bytes resolved up front into a plain lookup table; a picture-only paragraph isn't empty (P1-32, 2026-09-17)

Extracting a picture needs the zip package (to read and sniff the relationship's target bytes), but `document.go`'s token walker is deliberately pure — no I/O — so `docx.go`'s `Convert` now resolves every image-type relationship into a `resolvedImage` (`images.go`) *before* parsing starts: read via a new `readImagePart` (the existing `readPart`, generalised to take a caller-supplied limit so the per-image 20 MB cap and the whole-document 300 MB one compose correctly), sniffed with the same JPEG/PNG/GIF/WebP check `internal/kb/images.Store` uses for a real upload (re-implemented rather than imported, so this package stays free of any dependency beyond the standard library on this path), and never even attempted for a `TargetMode="External"` relationship. `parseBlocks` and its recursive re-parses (table cells, text boxes) now take a `*docCtx` bundling this lookup table alongside styles/hyperlink-rels and the running `[]Image`/token-counter state a whole `Convert()` call accumulates — a `<w:drawing>` or `<w:pict>`/`<w:object>`'s `v:imagedata` just looks its relationship id up in the map, either emitting a real `<img>` (with a `cid:` token the caller replaces once it stores the bytes — a scheme the sanitiser already rejects for anything else, so a token the caller somehow fails to replace is dropped, not left dangling) or a `data-missing-kind` placeholder. Wiring this up caught a real bug the same session it was written: `paragraph.hasContent()` had to become its own check, separate from `plainText()`, because a paragraph holding *only* a picture or placeholder has no text at all — the existing "drop empty paragraphs" rule was silently eating every picture-only paragraph, images included, until the fix.

## D-30 Tables via struct-decoding a captured subtree, re-parsed recursively (P1-31, 2026-09-17)

A table's row/cell nesting is naturally tree-shaped, unlike the free-form run content the flat token walk (D-28) suits well — so `document.go`'s `parseBlocks` special-cases `<w:tbl>`: on seeing its start token, `encoding/xml`'s `DecodeElement` consumes the whole element into a small struct (`tables.go`'s `tblXML`/`trXML`/`tcXML`), with each cell's own content captured as raw XML via the `xml:",innerxml"` tag rather than further unmarshalled. That raw XML is then fed straight back into `parseBlocks` itself (wrapped in a throwaway root re-declaring every namespace this converter reads, since a captured fragment carries none of its own) — so a cell gets exactly the same marks/links/list handling as a top-level paragraph, and a table nested inside a cell is "flattened into paragraphs" (SPEC B4) for free: it decodes into its own `tableBlock`, which `flattenBlocksToParagraphs` then splices into the outer cell's paragraph list by reading each of its cells' paragraphs in order, since nothing asked it to stay a nested `<table>`. The same DecodeElement-and-recurse pattern handles `w:txbxContent` (a text box's paragraphs, queued until the anchoring paragraph closes so they land right after it, per SPEC B4) and, together with a new `skipDepth`-gated check before either DecodeElement result is used, `mc:Choice` — this converter understands none of the extensions a Choice branch `Requires`, so it always prefers `mc:Fallback`, and gating on `skipDepth == 0` stops a text box or table present in *both* branches (a modern shape alongside its VML fallback, in particular) from being counted twice. The overall document's XML depth was already checked once, over the whole file, before any of this runs; a subtree can never be deeper than the whole it came from, so none of the recursive re-parses need a depth check of their own.

## D-29 Links as a segment attribute, merged the same way as marks (P1-30, 2026-09-17)

Hyperlinks (`w:hyperlink` with an external relationship, and legacy `HYPERLINK` simple/complex fields) needed to compose with bold/italic — a link can span a bold run and a plain run, and P1-29's segment model already merges adjacent same-formatting text into one span. Rather than a separate "link span" concept layered on top, `segment` gained an `href` field alongside `bold`/`italic`, resolved into a single `hrefStack` in `document.go`'s token walker (pushed by `w:hyperlink`, or by a `w:fldChar` "separate" once its instruction text parses as an external `HYPERLINK`, or by `w:fldSimple`'s own `w:instr` attribute; always popped at the matching end, even when nothing resolved, so an internal-anchor-only link or an unrecognised field still keeps its plain text with no href). Rendering became a two-level merge in `result.go`: group consecutive segments by `href` first (so a link spanning differently-formatted runs becomes one `<a>`, not several), then within each group, merge by bold/italic exactly as before. Lists are the one genuinely new structural piece: `paragraph` gained `directNumID`/`directIlvl`, resolved against either the paragraph's own `w:numPr` or (SPEC B4) its style's, via a new `styleSheet.numbering` basedOn-chain walk mirroring the existing outline-level one; `buildResult` groups consecutive same-numId paragraphs (after filtering empty ones, so a blank line doesn't split a list) and `renderList` builds the nested `ul`/`ol` structure with a small level stack, looking up each level's bullet-vs-other format in a new `numberingSheet` (`numbering.go`) parsed from `numbering.xml`.

## D-28 A per-run segment model for docx paragraphs, and a real fixture bug it caught (P1-29, 2026-09-17)

`internal/kb/docx`'s P1-11 spike reduced each `<w:p>` to one flat text string, enough for title/heading extraction but not for run-level formatting. P1-29 changes `paragraph` to hold `[]segment` (each a run of text with its own resolved bold/italic, or a line break), so a paragraph can mix "<strong>Sam</strong> before ordering more <em>toner</em>" in one line; `renderParagraphHTML` re-merges adjacent segments with identical formatting before emitting marks, so two runs split mid-word (a real Word artifact) still read as one word instead of two suspiciously-adjacent elements. Building this exposed a genuine bug in the P1-11 fixture generator: `image()`, `chartFrame()`, `smartArtWithFallback()` and `drawnShapeNoText()` all return a bare `<w:r>`, but several call sites in `sample.go`/`googledocs.go`/`big.go` spliced that bare run directly into the body as a sibling of `<w:p>` elements — not valid WordprocessingML (every `w:r` belongs to some `w:p`), and it silently discarded that content: the flat parser only ever appended a paragraph's `segments` to the result slice when its `<w:p>` closed, so text captured into a stray, paragraph-less run built up on a `paragraph` struct that had already been appended (or never would be) and was simply lost when the next real `<w:p>` overwrote it. Fixed by wrapping every such call in `p("", ...)` at its call site, and, defensively, by having the parser ignore a `<w:r>` encountered outside any `<w:p>` rather than silently losing whatever it captures.

## D-27 @verify-prev is skipped, not failed, when PREV never seeded anything (P1-28, 2026-09-17)

Implementing real `@seed`/`@verify-prev` content turned a CI-only bug from silent to loud: `run_upgrade_rollback_test`'s phase 2 always ran `@verify-prev` unconditionally, which is fine while it's a no-op placeholder but genuinely fails once it actually looks for seeded content — because PREV, right now, is always v0.0.1 (the highest existing tag until v0.0.2 is tagged), which predates the smoke-test harness and so never ran `@seed` in phase 1 to begin with. `run_prev_smoke` already had exactly the right check (does PREV's worktree even have smoke spec files?) for skipping phase 1 and phase 3's smoke assertions in this situation; phase 2's `@verify-prev` call now shares that same precomputed `prev_has_smoke_tests` flag instead of running unconditionally, so it's skipped for the same reason rather than failing against data that could never have existed. This is a bootstrap-only gap: once v0.0.2 is tagged and becomes PREV for some later `[container]` push, phase 1 seeds real content and `@verify-prev` runs and means something, same as gate 1.42 has always intended.

## D-26 container-test.sh reads its image tag from deploy/truenas.yaml instead of a hardcoded copy (P1-28, 2026-09-17)

## D-25 Fixed article identity, unique person, single-worker smoke project (P1-28, 2026-09-17)

`@seed`/`@verify`/`@verify-prev` (`e2e/smoke/basic.spec.ts`) prove gate 1.42 (an upgrade or rollback never loses Knowledge Base data) using content a later release's own `@verify-prev` has to recognise without having created it — so the article title and category name are fixed literals, not `uniqueName()`. The person who creates it, though, is a fresh one from `signInAsNewPerson`: `container-test.sh`'s upgrade/rollback harness runs `@seed` a second time against the *same* data folder once the build under test comes up (its phase 2, before the volume is ever wiped), and a fixed person name would collide with gate 1.06's duplicate-name refusal on that second run, where a category or article with a repeated name simply becomes a second row — harmless, and `@verify`/`@verify-prev` already select "the most recently updated" match rather than assuming there's only one. Locally, without `BASE_URL`, the `smoke` project also now runs with `workers: 1` (`playwright.config.ts`) for the same reason `speed` does (D-24): `@seed` and `@verify` only make sense run back-to-back against the one server that `@seed` just wrote to, and Playwright's worker-scoped `server` fixture gives every worker its own separate, empty database, so more than one worker silently breaks this suite's whole premise.

## D-24 Seeder design and timing method for speed tests (P1-27, 2026-09-17)

`e2e/seed` is a plain Go program, not a Playwright helper, so it can call `internal/kb`'s store types directly (`ArticleStore.Publish`, `CategoryStore.Create`, `images.Store.Save`) the same way the real app does, rather than re-implementing publish-and-sanitise logic over HTTP. It always runs to completion and exits *before* the real comphq binary opens the same `comphq.db` — the two never hold the file open at the same time — so there's no need to worry about SQLite's single-writer limit (D-02) between them. A single `math/rand` source seeded with a fixed constant drives every word, title and image chosen, so two runs with the same flags produce byte-identical content; that determinism is what makes a slow speed run reproducible rather than a one-off. The speed Playwright project (`e2e/speed/fixtures.ts`) seeds once by running with a single worker (`workers: 1` in `playwright.config.ts`) rather than by hand-rolling a global setup step, since a worker-scoped fixture already seeds exactly once per worker — one worker makes that a true "once" instead of once per parallel shard, and also keeps the timing measurements themselves free of CPU contention from other workers' tests. Timing itself uses plain `Date.now()` around `page.goto`+`data-ready`/`page.fill`+panel-visible/`page.request.get`, not Playwright's tracing API or `performance.now()` inside the page: SPEC B7's budgets are described in wall-clock terms a person would notice, and the median-of-5 (navigation, panel) or p95-of-50 (search endpoint) aggregation absorbs the noise a simple wall-clock timer carries.

## D-23 The server marks every matching block including the title; the client alone picks which to scroll to (P1-26, 2026-09-17)

A search result links to an article as `?q=<query>#b-<block>` (SPEC B4), but browsers never send the `#` fragment to the server, so the handler that renders the article page can't know which block the link meant to point at — only the query. The fix is to have the server compute every block the query matches (via `search.HighlightMatches`) and mark each one with a `data-hl` attribute holding its highlighted HTML, then let `highlight.js` — which alone can read `window.location.hash` — pick the one to scroll to and add the visible highlight class; every other matched block still gets highlighted in place, just without the scroll. This needed a block 0 for the title too: bm25 weights title matches 10x, so a query that matches an article's title often ranks the title as that article's single best-ranked block, meaning a real result can link to `#b-0`. The title lives outside `.kb-article-body` as its own `<h1>` rather than inside the sanitised `body_html`, so it needed its own `data-b="0"`/`data-hl` attributes threaded through a new `TitleHighlight` field, and `highlight.js`'s query scope had to widen from `.kb-article-body` to `document` to find it.

## D-22 Archive/unarchive share the article's current version_no (P1-24, 2026-09-16)

Every `kb_article_versions` row needs a `version_no` (SPEC B3), but archiving and unarchiving don't change an article's content — only its status — so they don't bump `kb_articles.version_no` the way a real edit does. Instead they insert a history row stamped with the version_no the article already has, holding a snapshot of the current title/category/body. That means two rows can share a version_no (e.g. an "edited" row and a later "archived" row both at version_no 3) — harmless, since `GET .../versions/{n}` just needs any row with that number, and they always agree on content. The alternative (bumping version_no on every status change too) would make "version 4" sometimes mean "different text" and sometimes "same text, different status," which is a worse distinction to explain than "some history rows share a number."

## D-21 A per-worker fixed loopback address for the SSRF test override (P1-23, 2026-09-16)

`COMPHQ_TEST_ALLOW_FETCH_HOST` (honoured only under `COMPHQ_TEST_MODE=1`) is read fresh from the environment on every fetch, which works for Go tests (`t.Setenv` mutates the same process) but not for E2E: the comphq binary is a separate OS process, spawned once per Playwright worker, and nothing can inject an env var into it after that. So `e2e/helpers/fixtures.ts` now reserves a *second* free port per worker at spawn time — alongside the comphq port it already allocated — fixes `COMPHQ_TEST_ALLOW_FETCH_HOST` to that `host:port` for the whole worker's lifetime, and exposes it as `server.stubImageHost`. A test that needs a reachable stub image server binds one to exactly that address (`e2e/helpers/stub-image-server.ts`); a test proving the failure path just points at that same address without starting anything, since a worker runs its own tests one at a time, so only one test ever holds the slot. `ArticleStore.Publish` also gained a transient `Article.ImageFailures` field (never written to the DB) rather than changing its return signature, since only two call sites care about it and every existing caller and test stays untouched.

## D-19 Draining the request body before responding to an oversize upload (P1-21, 2026-09-16)

`internal/kb/images.Store.Save` reads only `MaxBytes+1` bytes via `io.LimitReader`, so an oversize upload leaves the rest of the body still arriving on the wire when `handleUploadImage` writes its 400 response. The E2E oversize test caught this directly: the browser's `fetch()` reported a generic network failure instead of delivering the 400, because the connection broke while the client was still sending. The fix is to `io.Copy(io.Discard, r.Body)` before writing the response in that one branch, so the client finishes uploading into the void and then cleanly receives the "larger than 20 MB" message. The other rejection (`ErrUnsupportedType`) doesn't need this — `Save` already read the whole body before sniffing it.

## D-18 Editor's initial content as JSON data, not an inline script; spike tests retired (P1-20, 2026-09-16)

## D-16 Sanitiser link/image rules run as a custom pass after bluemonday (P1-18, 2026-09-16)

`internal/kb/html` uses `bluemonday` for the structural allowlist (tags and simple attributes like `colspan`/`rowspan`) but not for its own URL scheme/path checks. bluemonday's `RequireParseableURLs`/`AllowURLSchemes` validate `href` and `src` the same way across every element and reject relative URLs unless `AllowRelativeURLs(true)` is set globally — there's no way to say "keep the `<a>` tag but drop a `javascript:` href" (its default is to unwrap the whole element) while separately saying "drop the whole `<img>` unless `src` starts with `/images/`" (an attribute-value regex on `src` still leaves `alt` behind, so a bare `<img alt="...">` survives instead of disappearing). So `Sanitize` lets bluemonday allow `href`/`src`/`alt` unconditionally, then runs its own tree walk afterward: `fixLink` strips `href` unless its scheme is http/https/mailto and always adds `rel="noopener"`; `pruneInvalidImages` removes the `<img>` node outright unless `src` matches `^/images/`.

## D-17 Testing Publish's transaction rollback without a trigger on kb_search (P1-19, 2026-09-16)

## D-10 FTS5 query shape and markers (P1-08, 2026-09-16)

Confirmed `modernc.org/sqlite` v1.58.0 supports FTS5 `bm25()`, `snippet()` and `highlight()` identically to upstream SQLite, on Windows (dev) and Linux (CI) — no caveats found. Query building (`internal/kb/search.BuildQuery`): extract letter/digit runs only (`[\p{L}\p{N}]+`), discarding everything else, so raw user input can never inject FTS5 operator syntax; quote every run (`"word"`), which also defuses bareword operators like `AND`/`OR`/`NEAR`; suffix the last run with `*` for a prefix match — FTS5 allows `*` directly after a quoted string's closing quote for exactly this. Fewer than 2 significant characters yields no query at all (`ok = false`), rather than asking FTS5 to match everything or erroring. Snippet/highlight markers are the private-use characters U+E000/U+E001: they can't appear in real content and pass through `html.EscapeString` untouched, so the safe order is always escape-the-text-first, then replace markers with `<mark>`/`</mark>`. One gotcha: `snippet()` supports column index `-1` ("pick the column with the most matches"), but `highlight()` does not — `HighlightBlock` picks the column itself (0 for the title block, 1 for a body block) since SPEC B3 already tells us which one has content per row.
